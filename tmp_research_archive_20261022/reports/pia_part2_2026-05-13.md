## Section 6: PIA briefing system

### 6.1 Scheduling and generator

The v5 PIA briefing runs on the **same scheduler thread as v4**, in
`morning_briefing.py`. There is **no separate cron/service** — both are
fired from the same scheduler loop.

Sessions (`/opt/tradingbot/morning_briefing.py:336`):

```
_SESSIONS_V5: List[tuple] = [(5, 30, "London"), (12, 30, "NY")]
```

So **v5 PIA fires at the same 05:30 UTC and 12:30 UTC slots as v4**
(`_SESSIONS_GMT` / `_SESSIONS_BST` at lines 84-85 are also
`[(5, 30, "London"), (12, 30, "NY")]`). Both schedules are pure UTC year-round.

The actual generator hook (`/opt/tradingbot/morning_briefing.py:3778-3807`):

```python
# ── v5 (briefing.v5_pia) parallel fires ──────────────────────────
# Runs alongside v4 — separate dedup map, separate output dir.
# Disable via BRIEFING_V5_ENABLED=0.
try:
    from briefing.v5_pia.config import BRIEFING_V5_ENABLED as _V5_ENABLED
except Exception:
    _V5_ENABLED = False
if _V5_ENABLED:
    for s_hour, s_min, s_name in _SESSIONS_V5:
        sched_mins_v5 = s_hour * 60 + s_min
        elapsed_v5 = now_mins - sched_mins_v5
        if elapsed_v5 < 0 or elapsed_v5 >= SESSION_WINDOW_MINUTES:
            continue
        v5_key = f"v5:{s_name}_{today}"
        with _BRIEFING_V5_LOCK:
            if v5_key in _BRIEFED_SESSIONS_V5:
                continue
            _BRIEFED_SESSIONS_V5[v5_key] = today
        logger.info(...)
        try:
            from briefing.v5_pia.orchestrator import generate_v5_for_session
            generate_v5_for_session(s_name)
        except Exception as exc:
            logger.warning(...)
```

The orchestrator entry point is
`briefing.v5_pia.orchestrator.generate_v5_for_session()` at
`/opt/tradingbot/briefing/v5_pia/orchestrator.py:401-436`, which iterates
`pair_config.PAIRS` and calls `generate_briefing_v5(pair, session, now_utc)`
per pair (line 168).

Note on the v4 schedule (same file, line 84):

```
_SESSIONS_GMT: List[tuple] = [(5, 30, "London"), (12, 30, "NY")]
_SESSIONS_BST: List[tuple] = [(5, 30, "London"), (12, 30, "NY")]
```

So v4 and v5 fire at **exactly the same trigger times**, in the same
scheduler thread, on the same minute. Their outputs land in different
directories (next sub-section).

(RSI 70), explicit timeframe (5M). v4 also emits a structured
`entry_trigger_v2` array with discrete `{type, level, tolerance_pips}`
clauses so an executor can deterministically check entry conditions.
**v4 score: 3/3** — these are programmer-grade triggers.

**v5** — every single briefing is STAND_ASIDE. The non-STAND_ASIDE
schema would be:

```
{"entry": <float>, "stop": <float>, "target": <float>,
 "bias_anchor": <H4 EMA20 value>, "stop_structural_level": "swing_low"|...}
```

i.e. a single price (typically H4 EMA20) with no entry trigger
indicator confirmation. The PIA rationale_writer system prompt
explicitly forbids the LLM from inventing levels and is constrained to
"We look to Buy at {entry}" style sentences. When v5 actually arms,
its entry is fully concrete (single price + RR-bounded SL/TP), but
v5 does not specify an entry trigger condition — the executor
(`briefing/v5_pia/executor.py`) waits for price to touch entry ±2 pips
and fires. **v5 score: 2/3** — entry/SL/TP fully concrete and
machine-checkable, but no confirmation trigger (RSI/close-back).

#### Trading plan cleanliness

**v4**: 5-6 plans per briefing, mix of LONG/SHORT in same briefing
(e.g. 2026-05-12 London GBPUSD had plans 1,4,6 LONG and 2,3,5 SHORT).
Entry zones can overlap (plan 2 zone [13625, 13632] vs plan 5 zone
[13620, 13632] in the same briefing). SL/TP not on the per-plan
field (plan-level `stop_loss_pips`/`tp1_pips` consistently null in
the inspected briefings; they live on the `best_trade` conditional
branch instead).

**v5**: At most 1 trade plan per briefing. No overlap by construction.
SL and TP are explicit prices (when armed). When STAND_ASIDE, no plan
at all. Cleanliness is dramatically higher — but the cost is total
abstention in this sample.

#### Counter-trend handling

v4 has a `scenarios` field with 3-4 ranked alternative paths, each with
own `trigger` / `target` / `invalidation`. Example
(2026-05-13 London GBPUSD scenarios):

```
"label": "Pre-news sweep low, post-news reversal higher", probability 0.4
"label": "Bullish GBP data drives breakout above 13548",  probability 0.3
"label": "Bearish GBP data drives breakdown below 13515", probability 0.3
```

v4 also has a `best_trade` field with `mode=CONDITIONAL` and a
`conditional_branches` array that explicitly forks on data outcome.
This is a real counter-trend hedge — the briefing tells the executor
"if A happens go long, if B happens go short". The morning_briefing
SYSTEM_PROMPT explicitly asks for "scenarios" and probabilities at
`/opt/tradingbot/morning_briefing.py:182`+.

v5 has **no** alternative-scenario field. The schema is strictly
single-direction (BUY / SELL / STAND_ASIDE). When the H4 EMA and D1
EMA disagree, v5 abstains entirely — by design (see
`trade_plan_builder.py:127-132`). There is no plumbed counter-trend
plan.

**Counter-trend anticipation by v4**: 2026-05-11 USDJPY where v4 daily
called BEARISH but USDJPY closed BULL +29.3 — the v4 scenarios field
on that briefing was not inspected programmatically here, but the v4
schema has the affordance. **v5 cannot anticipate counter-trend by
construction.**

## Section 9: PIA architecture differences

### 9.1 LLM call: separate prompt or separate model?

Both v4 and v5 hit the **Anthropic /v1/messages** endpoint. The
v5 wrapper at `/opt/tradingbot/briefing/v5_pia/anthropic_client.py:19`
explicitly imports auth from v4:

```python
from morning_briefing import ANTHROPIC_API_KEY, ANTHROPIC_URL
```

Same vendor (Anthropic), same endpoint. Different model:

- v4: `claude-sonnet-4-5` — `/opt/tradingbot/morning_briefing.py:55`
  (`ANTHROPIC_MODEL: str = "claude-sonnet-4-5"`)
- v5 rationale: `claude-sonnet-4-6` — `/opt/tradingbot/briefing/v5_pia/rationale_writer.py:29`
  (`RATIONALE_MODEL = "claude-sonnet-4-6"`)

Different sampling:

| Param        | v4 (morning_briefing) | v5 (rationale_writer) |
|--------------|-----------------------|------------------------|
| Model        | claude-sonnet-4-5     | claude-sonnet-4-6      |
| Temperature  | 0.3 (env override `BRIEFING_TEMPERATURE`) | 0.2 |
| max_tokens   | 12000 (env `BRIEFING_MAX_TOKENS`) | 250 |
| Timeout      | API_TIMEOUT (module-level) | 60s |

System prompt locations:

- v4: `/opt/tradingbot/morning_briefing.py:168-180` — "professional FX
  market analyst with deep expertise in technical analysis... You
  produce a structured JSON briefing only — no prose, no markdown."
- v5: `/opt/tradingbot/briefing/v5_pia/rationale_writer.py:52-82` — "PIA-First
  house style... Your only job is to write the rationale field... 4-6
  short lines, declarative, present tense... Output: plain text, no
  markdown, no preamble."

The two prompts have fundamentally different goals: v4 asks the LLM
to **produce the entire briefing** (bias, levels, plans, scenarios,
news context, signal_filter). v5 asks the LLM to **write a 4-6 line
prose rationale** over a pre-computed deterministic plan. v5 is
**post-hoc narration**, not analysis.

### 9.3 Post-processing differences

v4: LLM produces JSON, code post-validates levels (`_call_anthropic_once`
has a levels validation + retry loop at line 2882+). The LLM is allowed
to set `daily_bias`, `session_bias`, `signal_filter`, all `trading_plans`,
all `scenarios`, etc. — the model has discretion over almost every field.

v5: LLM has **zero discretion over decision-grade fields**. The rationale
writer prompt is explicit at
`/opt/tradingbot/briefing/v5_pia/rationale_writer.py:59-64`:

```
You MUST NOT:
- Change the direction, entry, stop, target, or confidence values
- Invent new levels not in support_levels or resistance_levels
- Reference levels by name that aren't in the bias_anchor_label or
  stop_structural_level fields
- Recommend exit management, partial fills, or news handling
```

Direction, entry, stop, target, confidence_bucket are all set by
`trade_plan_builder.py` + `confidence_scorer.py` BEFORE the LLM is
called. The orchestrator writes the briefing to disk with
`rationale=null` first (line 298), then calls the LLM, then re-writes
with rationale populated (line 363). If the LLM fails the trade plan
already survives on disk untouched.

v5 schema validation is via pydantic (`BriefingV5.validate()` at
`orchestrator.py:152`); v4 has ad-hoc level-validation only.

### 9.4 Smoking gun

The single most important architectural difference is this gate in
`/opt/tradingbot/briefing/v5_pia/trade_plan_builder.py:127-132`:

```python
if d1_bull and h4_bull:
    direction = "BUY"
elif (not d1_bull) and (not h4_bull):
    direction = "SELL"
else:
    return _stand_aside("d1_h4_bias_disagree")
```

v5 abstains whenever D1-EMA20 and H4-EMA20 disagree on direction. v4
has no such hard gate — it lets the LLM weigh structural conflict
against session dynamics and produce a `session_bias` that can run
counter to `daily_bias`. The 5/11–5/13 sample is dominated by exactly
this conflict (e.g. 5/12 USDJPY: D1 bearish, H4 bullish → v4 produces
a LONG primary that captured the +41.5 pip move; v5 abstains).

In one sentence: **v5 is a deterministic confluence-scorer that uses
an LLM only for prose narration; v4 is an LLM-driven analyst that
makes all decisions in the model. v5's "PIA" output is the
confluence-scorer's verdict, not the LLM's view.**

## Section 10: Honest summary

### 10.1 Is PIA producing better directional reads than morning_briefing?

**We cannot tell from this sample. v5 PIA produced ZERO directional
calls in 20 paired briefings over the 2026-05-11 to 2026-05-13 window.**
Every v5 briefing was STAND_ASIDE — first 8 due to `insufficient_h4_bars`
(the H4 cold-start bug, partially fixed in commit f6b8599 but the cache
ceiling at ~10 H4 bars per pair leaves the system marginal), then 8 due
to `d1_h4_bias_disagree`, then 4 due to `no_target_meets_rr_threshold`.
The comparison log captures all 16 of the 5/11–5/12 rows as
`direction_agreement: V5_ABSTAIN`. v4 made 20 directional rank-1
plan calls in the same window with a primary-plan hit rate of 5/20 = 25%
(daily_bias hit rate 4/20 = 20%), which is low — but at least it's
non-zero and falsifiable. v5's hit rate is undefined because the
denominator is zero. Trigger-quality favours v4 (3/3 vs 2/3) because v4
emits structured `entry_trigger_v2` arrays with explicit indicator
thresholds, and v4 has a `scenarios`/`best_trade.conditional_branches`
field that anticipates counter-trend moves by construction; v5 has no
equivalent.

### 10.2 Decision recommendation

**Recommend EXPERIMENT, not promote or deprecate.**

This is the "can't tell from N days" case from the prompt's branching.
The promotion path is unsafe (v5 has zero positive evidence of
better calls, only zero evidence of bad calls — abstention is not
information). The deprecation path is premature (the H4 cold-start
fix only became active 2026-05-12 and the very next session showed
8/8 abstentions on a different gate — we have not yet seen v5 with
its full data window AND in a market where D1 and H4 agree).

The smallest deprecation lever, for reference: set
`BRIEFING_V5_PARALLEL_MODE=0` in `/opt/tradingbot/.env` (memory:
`project_v5_pia_phase3_executor_pending.md`) — this idles the
executor; the producer still writes JSONs but no trades fire under the
BRIEFING_V5 strategy tag. To stop writing JSONs (and the LLM API
cost) too, set `BRIEFING_V5_ENABLED=0` (see
`/opt/tradingbot/morning_briefing.py:3782`).

The smallest promotion lever would require first widening v5's data
window per memory `project_v5_pia_h4_cold_start_fix.md` (extend
rolling 5M cache to ≥1920 rows) AND relaxing the
`d1_h4_bias_disagree` hard gate to a confidence penalty rather than an
abstain — and that's not a config flip, it's a code change.

### 10.3 Smallest experiment to settle this definitively

**Run the comparison through 2026-05-23 with two changes, then re-score
on the 10-trading-day window 2026-05-12 → 2026-05-23.**

Decider metric: number of v5 ARMED briefings in the window.

- If v5 emits ≥ 6 ARMED briefings over those 10 days AND its
  per-trade win rate ≥ v4 BRIEFING_EXECUTION's win rate in the same
  window → promote.
- If v5 emits < 6 ARMED briefings → the
  `d1_h4_bias_disagree` gate is too strict for current market regime;
  deprecate v5 (set `BRIEFING_V5_PARALLEL_MODE=0`,
  `BRIEFING_V5_ENABLED=0`) or relax the gate. Either way, the
  current implementation is not earning its API spend.
- If v5 emits 6+ ARMED briefings but loses worse than v4 → deprecate.

Explicit threshold: 6 ARMED briefings = roughly 1 ARMED every 2 trading
days = enough to compute a binomial confidence interval on win rate
that excludes 50% at p<0.10. Below that, the dataset is too sparse for
any honest call.

Two changes needed before starting the experiment window:

1. Extend the rolling 5M cache window (memory's
   `project_v5_pia_h4_cold_start_fix.md` recommends ≥ 1920 rows /
   ~6.7 days, which gives the full 40 H4 bar spec window). Without
   this, level-discovery in v5 stays thin even after the cold-start
   fix.
2. Make sure the comparison capture script runs on a timer/cron at
   12:30 UTC and 21:30 UTC daily, or as a systemd timer. Right now it
   has only 16 rows for 2 days; nothing seems to be invoking it
   automatically (no reference in `morning_briefing.py`,
   no `.service`/`.timer` found in `/opt/tradingbot/deploy/systemd/`
   for it). Without automated capture, the 10-day comparison the user
   pre-committed to in memory `project_v5_pia_h4_cold_start_fix.md`
   cannot be evaluated.

The comparison logger should be run for the missing 2026-05-13 London
row (5 backfill invocations like
`python3 /opt/tradingbot/scripts/v5_pia_comparison_capture.py --backfill-date 2026-05-13 --session London`)
to bring the dataset current today.
