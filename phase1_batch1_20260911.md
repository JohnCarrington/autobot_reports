## F. Candidate Contract (actual schema)

```python
@dataclass(frozen=True)
class Candidate:
    # Identity
    candidate_id: str
    timestamp: str
    epic: str
    pair: str

    # Detection
    strategy: str
    strategy_family: str        # one of FAMILY_* — bounded vocabulary
    side: str                    # "LONG" | "SHORT"
    opportunity_type: str        # one of OPPORTUNITY_*

    # Proposed order geometry
    candidate_price: float
    proposed_stop: Optional[float]
    proposed_target: Optional[float]

    # Provenance & context
    source_path: str             # one of SOURCE_*
    day_type_raw: Dict[str, Any]
    market_state_snapshot: Dict[str, Any]
    reason_codes: List[str]
    mechanical_valid: bool = True
    metadata: Dict[str, Any]
    event_id: Optional[str] = None

    # Detection lineage
    first_detected_ts: Optional[str] = None
    first_actionable_ts: Optional[str] = None
```

**Invariants** (enforced in `__post_init__`, `ValueError` on breach):

- All identity + detection fields are non-empty.
- `side ∈ {LONG, SHORT}`.
- `candidate_price` is numeric.
- Instance is frozen — no mutation after construction.
- **No method on Candidate can execute, fire, or amend anything** — verified by `test_phase1_candidate_contract::test_candidate_cannot_execute_or_side_effect`.

Vocabulary constants:

- `FAMILY_*` (23 values): BB_BOUNCE, LEVEL_BOUNCE, EMA_PULLBACK, STRUCTURE_BREAK, TREND_V3, BRIEFING_EXECUTION, BRIEFING_V5, BRIEFING_LIQUIDITY, BRIEFING_SWEEP, BRIEFING_HUNT, PIA_FIRST, NEWS_STRATEGY, NEWS_TICK, NEWS_CONTINUATION, PIVOT_BREAK, H1_PIERCE, CONFIRMATION_FALLBACK, BB_REVERSAL_PATTERNS, QM_V2, LIQUIDITY_SWEEP, WINDOW_SWEEP, UNKNOWN.
- `OPPORTUNITY_*` (10 values): TREND_CONTINUATION, TREND_PULLBACK, BOUNCE, REVERSAL, BREAKOUT, LIQUIDITY_SWEEP, NEWS_FADE, NEWS_CONTINUATION, BRIEFING_PLAN, UNKNOWN.

## H. Outcome-Grader Design

**Module:** `outcome_grader.py`. Two public entrypoints:

1. **`grade(anchor_ts, side, entry_price, pair, proposed_stop, proposed_target, get_bars_after, horizon_bars=240, excursion_window_bars=20) -> OutcomeGrade`**

   Grades an anchor point against a callable that returns subsequent 5m bars. Bar source is injected so the grader is source-agnostic (production wires it to `candle_builder.get_df`; tests wire fixtures; the replay harness wires cached CSVs from `data/candles/`).

   Outputs (`OutcomeGrade` dataclass):
   - `mfe_pips`, `mae_pips`
   - `time_to_mfe_min`, `time_to_mae_min`
   - `excursion_20bar_pips`, `drawdown_20bar_pips` (spec §118G fixed horizon)
   - `target_first`, `stop_first` (booleans; `None` when only one side supplied)
   - `horizon_bars_evaluated`
   - `graded_at_ts`, `grader_version` ("phase1.0")

2. **`grade_qm_candidate_row(row, *, get_bars_after) -> Dict`**

   Grades a QM candidate row from `logs/qm_candidates.jsonl` **without enabling QM live fire**. This closes Phase 0's finding that 670/670 QM candidates carry empty outcome dicts. Direction is inferred from `hypothetical_entry` vs `hypothetical_stop`; the original (empty) outcome is preserved under `outcome_prior` for auditability.

**Grading pass — how it becomes actionable:**

Batch 2 will add a nightly cron (`scripts/grade_candidate_corpus.py` — not yet implemented) that:
1. Iterates rows in `logs/candidate_corpus.jsonl` (and `logs/qm_candidates.jsonl` for the QM shadow).
2. For any row without a graded outcome AND whose anchor + 20 bars are complete in `data/candles/<PAIR>/`, calls `grade()` and writes a companion `logs/candidate_corpus_graded.jsonl` row keyed by `candidate_id`.
3. Idempotent — repeated runs skip already-graded rows.

The grader never touches broker state and cannot open, close, or amend a position. It is a pure OHLC-in / metrics-out function.

### K.3 Why every row is `deferred_to_batch_2`

The harness cannot compute a "new orchestrator/gate would have said X" verdict without a candidate object corresponding to each old attempt. Two options exist for producing that verdict:

1. **Shadow-migrate the dispatch sites** so each `execute_trade(...)` in autobot.py also calls `orchestrator_v2.submit(candidate)` in shadow mode. Then the corpus fills in real time, and each signal_log row has a matching corpus row for the diff. This is Batch 2.

2. **Historical fabrication** from signal_log fields alone. This is FORBIDDEN under Phase 1 §12 anti-leakage: reconstructing a candidate from a signal_log row means the "detection" carries knowledge of what happened after (close_reason, pnl_pips) — the diff would be meaningless.

Batch 1 therefore delivers the harness structure and the enumeration; Batch 2 will deliver the concrete diff artifact once shadow migration produces corpus rows to compare against.
