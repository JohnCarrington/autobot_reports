## 1. T2 — auth halt

### The evidence that was asked for

The exit-78 machinery already existed. Its three pieces, quoted:

```
/etc/systemd/system/autobot.service:12
    Restart=on-failure

/etc/systemd/system/autobot.service.d/auth-suspension-guard.conf:13
    RestartPreventExitStatus=78

autobot.py:6202                          # the line that exits 78
    raise SystemExit(FATAL_AUTH_EXIT_CODE)
ig_auth.py:108
    FATAL_AUTH_EXIT_CODE = 78
```

So `Restart=on-failure` relaunches on any non-zero exit **except** 78, and the
`__main__` handler converts `FatalAuthError` into exactly that exit.

### The gap it did not cover

That path only fires on a *login* whose error body carries a known fatal
marker. A session that is already established and then starts being refused —
token revoked, key disabled mid-run — raises nothing, so the process keeps
hammering IG. That is the same clock-resetting behaviour the guard exists to
prevent, entered through a different door.

**This is not hypothetical.** On 2026-07-22 at 21:03 the journal shows:

```
[LS-RECOVER] refresh_session failed: FatalAuthError('HTTP error: 403
    {"errorCode":"error.security.api-key-disabled"}') (continuing with cached session)
[LS-RECOVER] attempt 1 FAILED: ... sleeping 5s before retry
[LS-RECOVER] attempt 2 FAILED: ... sleeping 10s before retry
[LS-RECOVER] attempt 3 FAILED: ... sleeping 30s before retry
[LS-RECOVER] attempt 4 FAILED: ... sleeping 60s before retry
```

`FatalAuthError` was raised, caught locally, logged as a warning, and the
process carried on retrying against a disabled key. Exit 78 was never reached.

### What was built

A consecutive-non-200 counter on the response hook already installed on the
IGService session (`ig_auth._log_non_200_response`). 200 resets it. At the
threshold it logs `[AUTH-HALT]` with the raw body, writes the fatal-auth
sentinel, sends one Telegram, and arms. `check_auth_halt()` — polled by the
main loop at `autobot.py:6180` — raises `FatalAuthError`, so the halt travels
the **existing** route rather than adding a second mechanism. Graceful
shutdown still runs.

Raising from inside the hook was rejected deliberately: that hook executes
inside whatever request is in flight, which can be an order placement.

### The benign-marker exemption, and why a bare counter would have been wrong

Every non-200 this box saw in the month to 2026-07-30:

```
  23 x  412 PUT /gateway/deal/session   error.switch.accountId-must-be-different
   1 x  404 GET /gateway/deal/confirms/<ref>
```

All 23 are IG's no-op reply when the requested account is already current, and
**two arrived in the same second on 2026-07-27**. A bare consecutive-non-200
counter at threshold 3 would eventually have armed on that burst and halted
live trading with no restart, for nothing. The 412 marker is exempted — it
neither arms nor resets — and the exemption is evidence-cited in the code.

One landed during this very restart (22:06:49) and was correctly ignored.

Config: `AUTH_HALT_ENABLED=1`, `AUTH_HALT_CONSECUTIVE_NON_200=3`.

## 3. T4 — blackout fallback repoint

### Current behaviour when `register_window` is empty AND the file is stale — as asked, reported not changed

`news_windows.json` was last edited 2026-05-13; its newest event was
**2026-04-14**. `is_news_blackout()` looks up today's date key, finds nothing,
and returns `(False, "")`.

The failure is silent by construction. `_windows` is *non-empty* — it holds 12
stale dates — so the `not _windows` early-return never triggers. There is no
error, no warning, and no distinction between "no event today" and "this file
stopped being maintained 107 days ago". **From 2026-04-15 the gate has blocked
nothing**, and `register_window()` calls from the briefing were the only thing
keeping any blackout alive at all.

The staleness guard makes this visible. It deliberately does **not** start
blocking — a guard that begins blackouting on a config problem is worse than
one that is quiet about it. There is a test pinning exactly that.

### `register_window` is global, not per-pair — confirmed, no change

```
news_blackout.py:39    _windows: dict = {}                                # {date: [HH:MM]}
news_blackout.py:180   def is_news_blackout(utc_dt: datetime) -> Tuple[bool, str]
news_blackout.py:208   def register_window(date_key: str, time_utc: str) -> None
```

Neither function takes a symbol, and the store is keyed by date alone. A
window registered from **any** pair's briefing news_context blacks out **every**
pair. Understood and left as-is.

### What was built

* `scripts/refresh_news_windows.py` — regenerates from Finnhub via
  `news_calendar` (the 161 repair pattern: direct fetch + timer). HIGH impact,
  USD/GBP/EUR/JPY/CAD, 7-day horizon, atomic temp-file-and-rename write. It
  **refuses to write an empty file**: an empty file reads as fresh to the
  staleness guard while blacking out nothing, which is the exact trap being
  escaped.
* `news-windows-refresh.timer` daily at 04:40 UTC — installed and enabled,
  ahead of both the 05:30 briefing and the 05:45 premarket check.
* Generated files carry `"_timezone": "UTC"` and skip the BST→UTC shift the
  hand-maintained file needs. **Without this every auto window would fire an
  hour early for roughly seven months a year.** Metadata keys are no longer
  mistaken for dates.
* `[BLACKOUT-STALE]` error log + Telegram, once per UTC day, past
  `NEWS_WINDOWS_STALE_DAYS=7`. Age comes from `_generated_at`, falling back to
  file mtime — so the old file would have been caught too, at 78 days.
* **Audit (a):** `[BLACKOUT-PAST-EVENT]` warning when `register_window()`
  receives a window that has already passed. It warns and still registers;
  silently dropping would be a behaviour change nobody asked for.

Live at restart:

## 6. T7

### (a) `priced_in` returned `insufficient_lookback_data` 21/21 — fixed

**Cause.** The guard looked up `df_5m["timestamp"]`.
`candle_builder._rebuild_symbol_dfs` builds the in-memory 5m frame as
`df[["time", "open", "high", "low", "close"]]` (candle_builder.py:362-365), and
`get_df()` hands that frame straight to the guard. The column has always been
`"time"`, so the lookup missed on **every** call and `_price_n_mins_ago`
returned `None`. The guard has never once had the data to form an opinion.

`"timestamp"` exists only in the *disk-cache writer*
(candle_builder.py:108-109), which renames `time`→`timestamp` on the way to
CSV. That is not the frame the guard receives — which is why a casual check
against the CSV cache looks fine and misleads.

**Lookback requirement, quoted.** `GUARD_PRICED_IN_LOOKBACK_MINS` (default 30),
matched to the nearest bar within a 4m59s tolerance — so it needs roughly 7
consecutive 5m bars. **What it receives: 600 bars.** The data was always there.

**Fix** — 12 lines in the DataFrame branch, inside the 20-line budget. Accepts
`timestamp`/`time`/`ts`/`datetime`/`date` plus a `DatetimeIndex`. Also switched
that branch to positional lookup: it resolved a label from the reset timestamp
series against the original frame, which silently falls through to the `None`
path whenever the frame is not RangeIndexed. That bug was caught by the new
DatetimeIndex test, not by inspection.

Verified on a live-shaped frame: old path → `None`; new path → the correct
6-bars-back close. The guard now returns `within_threshold` with populated
`price_then`/`move_pips` instead of abstaining.

> Noted while watching the restart: `[CACHE-AGE]` reports the 5m cache for two
> pairs as `STALE` with ~30 rows at boot (last_ts 2026-04-23), against 600 rows
> for the other two. Those pairs will keep abstaining until the live feed
> refills them. Not part of this task; flagging it because it bounds how soon
> the fix shows up for all four pairs.

### (b) Why the 2026-07-23 London briefing ran at 10:13 — evidence only

Not a scheduler fault. **The process was not running at 05:30.**

      (zero journal lines for ~13 hours)
2026-07-23 10:13:26  Applied trading_ig resolution patch (#22/#86).       <- new process
2026-07-23 10:13:38  [morning_briefing] Scheduler thread started

A line count over 21:10 → 10:13:20 returns **0**. The service was down across
the whole London window; the scheduler's catch-up path fired the missed

The outage itself traces to the `api-key-disabled` 403 storm quoted in §1 —

### (c) DEAL-08 (2026-07-22 15:25 USDJPY BUY) has no close row — resolved

**The position closed at the broker. The close event was missed because no
process was running to observe it.**

Open, confirmed at broker:

🟢 Opening BUY <USDJPY epic> size=2.0 stopDist=15.0 limDist=29.5
✅ IG response: {'date': '2026-07-22T15:25:01.799', 'status': 'OPEN',
   'reason': 'SUCCESS', 'dealStatus': 'ACCEPTED', 'dealId': <DEAL-08>,
   'level': 16311.0, 'stopLevel': 16296.0, 'limitLevel': 16340.5, ...}

`signal_log.jsonl` holds exactly **one** row for it — the open, with
`outcome: null` and no `timestamp_close`, `exit` or `pnl_pips` key at all. Of

The chain:

1. The fire happened at 15:25:01 and the process shut down at 21:07:29 — the

2. Nothing ran for ~13 hours.
3. At the 10:13 restart, reconcile reported **one** open position and one

   **DEAL-08 was not among them** — so IG no longer considered it open, i.e. it
   closed during the outage.
4. Reconcile-on-restart restores *open* positions. There is no back-fill for
   closes that completed while the process was down, so the row stayed open
   permanently.

Whether it exited at stop or limit is not determinable from on-host data, and I
did not open a broker session to ask — probing IG while the service is live
spawns a competing session. Report-only as instructed; no fix attempted.

> Side observation with diagnostic value: the `🟢 Opening` and `✅ IG response`

> are `print`-style stdout writes, block-buffered, and only flushed at process
> exit. Any live diagnosis that trusts the journal timestamp on those lines

## 9. Things worth knowing

**A `daemon-reload` happened mid-session, before the single restart.**
Installing the T4 timer required it. It also applied the previously-staged unit
Descriptions and the premarket timer repoint. `autobot.service` itself was
**not** restarted by it — `NRestarts=0` and an unchanged start timestamp
confirmed that at the time. The one service restart still happened at the end
as instructed.

`🛑 AUTH-HALT` message. Spurious — nothing was wrong with the box. Every
subsequent offline run stubs the sender, and the committed test suite injects a
stub module rather than importing the real one.

**A pre-existing test landmine, found and worked around, not fixed.**
Importing `telegram_alerts` anywhere before `test_news_strategy_rebuild.py`
makes 11 of its tests fail. Reproducible with a two-line file that does nothing
but `import telegram_alerts`. The T4 suite injects a stub into `sys.modules`
instead. Out of scope to fix, but it inflates the full-suite failure count and
will keep confusing anyone who bisects it.

**Full unit suite: 84 failed / 1076 passed / 21 skipped.** None of the failures
are in the 6 suites added here — all 64 new tests pass in the full run.
`test_fatal_auth_exit.py`, the suite closest to the T2 change, passes in
